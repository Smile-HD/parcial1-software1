# mobile-test-client Specification

## Purpose

An EXTERNAL thin client, built by hand and explicitly NOT generated by the tool. Its only job is to prove the generated backend (System B) is functional: run CRUD against it and exercise its offline assistant.

## Requirements

### Requirement: Explicitly Not Generated

The mobile test client MUST live outside the codegen output and MUST NOT be produced by `spring-codegen`. Codegen output MUST contain no client application.

#### Scenario: Client absent from generated output

- GIVEN a diagram is generated into a backend project
- WHEN the generated tree is inspected
- THEN it contains no mobile or web client application
- AND the test client resides in its own separate location

### Requirement: CRUD Against The Generated Backend

The client MUST perform create, read, update and delete against at least one entity exposed by the generated backend, using only that backend's HTTP API.

#### Scenario: Full CRUD cycle from the client

- GIVEN the generated backend is running locally
- WHEN the operator creates, reads, updates and deletes a record from the client
- THEN each operation succeeds in the UI
- AND the final read confirms the record no longer exists

#### Scenario: Backend down is reported clearly

- GIVEN the generated backend is not running
- WHEN the client attempts a request
- THEN the client shows an explicit connection error
- AND it MUST NOT display stale data as if it were live

### Requirement: Exercise The Offline Assistant

The client MUST invoke the generated backend's offline assistant and display its response, including the canned fallback path.

#### Scenario: Scripted assistant action from the client

- GIVEN the backend and its local model are running with internet disabled
- WHEN the operator asks the assistant to list records of an entity
- THEN the client displays the returned records

#### Scenario: Fallback surfaced to the operator

- GIVEN the operator sends an unmappable request
- WHEN the assistant returns the canned response
- THEN the client displays that response verbatim

### Requirement: Configurable Backend Endpoint

The client MUST allow the backend base URL to be configured without rebuilding, so it can target a local machine or LAN host during the demo.

#### Scenario: Retarget without rebuild

- GIVEN the client is running
- WHEN the operator changes the configured base URL to another host
- THEN subsequent requests go to the new host

### Requirement: Minimal Scope

The client SHOULD remain a thin demo harness: no offline caching, no auth, no multi-entity dashboards beyond what is needed to prove CRUD and the assistant.

#### Scenario: Scope check

- GIVEN the client implementation
- WHEN its feature surface is reviewed
- THEN it contains only endpoint config, CRUD on the demo entity, and the assistant view

## Acceptance Criteria

- [ ] Client lives outside codegen output; zero generated client code
- [ ] Full CRUD cycle succeeds against the generated backend
- [ ] Assistant invoked, both scripted action and canned fallback shown
- [ ] Backend URL configurable at runtime

## Cross-Cutting Concerns

- Consumes the API contract of `offline-backend-artifact` and `offline-ai-assistant`.
- Documented fallback: demonstrate the backend via a web/REST client if the mobile client is not ready.

## Open Questions

- Client technology is unresolved: web/PWA versus thin native. Pick before the tasks phase, since it drives effort and demo-day device setup.
